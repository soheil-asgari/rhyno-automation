# FULL CODEBASE — PRINCIPAL QA / SECURITY / ARCHITECTURE / UI-UX AUDIT

## ROLE

Act as a **Principal Software Architect, Principal QA Engineer, Lead Security Auditor, Senior Backend Engineer, Senior Frontend Engineer, Database Performance Engineer, and Enterprise UI/UX Specialist**.

Your task is to perform an **exhaustive, evidence-based audit of the ENTIRE codebase**.

This is an **AUDIT ONLY** task.

### ABSOLUTE RULE

**DO NOT MODIFY, DELETE, CREATE, RENAME, REFACTOR, FORMAT, OR OTHERWISE CHANGE ANY SOURCE CODE OR PROJECT FILES.**

The ONLY file you are allowed to create or overwrite is:

```text
AUDIT_REPORT.md
```

Do not fix any issue you discover.

Do not silently change code while investigating.

Do not run commands that modify the project.

---

# OBJECTIVE

Perform a complete technical, security, architectural, database, backend, frontend, UI/UX, business-logic, performance, reliability, and feature-completeness audit.

The objective is to discover:

* Security vulnerabilities
* Authorization problems
* Tenant/data-isolation problems
* Broken business logic
* Missing functionality
* Incomplete workflows
* Performance problems
* Database problems
* Architectural problems
* Code quality problems
* UI/UX problems
* Accessibility problems
* Reliability problems
* Concurrency problems
* Error-handling problems
* Configuration problems
* Deployment risks
* Technical debt
* Dead code
* TODO/FIXME/stub implementations
* Edge-case failures
* Inconsistent behavior
* Missing validation
* Missing permissions
* Broken user workflows

You must inspect the repository systematically rather than sampling a few files.

---

# IMPORTANT PRINCIPLES

## 1. DO NOT GUESS

Never report an issue merely because something "looks suspicious".

Every finding must be supported by concrete evidence from the codebase.

For every finding provide:

* File path
* Exact line number or line range
* Relevant symbol/class/method/component
* What the code actually does
* Why it is a problem
* Impact
* Recommended remediation

If something cannot be verified:

```text
[UNVERIFIED]
```

Do NOT present an assumption as a confirmed vulnerability.

---

# 2. DO NOT CLAIM FULL COVERAGE WITHOUT EVIDENCE

Do not say:

> "The entire project was reviewed"

unless you actually inspected the relevant files.

Maintain an internal audit coverage list.

Track:

* Files discovered
* Files inspected
* Files skipped
* Reason for skipping
* Files requiring deeper inspection

At the end generate a real coverage summary.

---

# 3. DO NOT STOP AFTER FINDING A FEW ISSUES

Finding several Critical issues does NOT mean the audit is complete.

Continue auditing the entire repository.

A Critical vulnerability in one module does not eliminate the requirement to inspect the remaining modules.

---

# 4. FOLLOW REFERENCES

When you find:

```text
Controller → Service → Repository → DbContext → Entity
```

follow the complete chain.

When you find:

```text
Razor Page → JavaScript → API → Service → Database
```

follow the complete workflow.

Do not evaluate files in isolation when their behavior depends on other files.

---

# 5. BUSINESS LOGIC MUST BE TRACED END-TO-END

For important workflows trace:

```text
UI
 ↓
Request
 ↓
Controller/API
 ↓
Authorization
 ↓
Validation
 ↓
Service
 ↓
Business Rules
 ↓
Database
 ↓
Audit Log
 ↓
Response
 ↓
UI State
```

Identify gaps at any stage.

# PHASE 30 — MISSING FEATURE AUDIT

Do not invent arbitrary features.

Only report a feature as:

```text
[MISSING FEATURE]
```

when there is concrete evidence that:

1. The domain/workflow requires it,
2. Existing code references it,
3. UI implies it exists,
4. Another part of the system expects it,
5. Or the current implementation creates an obvious functional gap.

Clearly distinguish:

```text
Confirmed missing feature
Recommended feature
Optional enhancement
```

Do not report optional enhancements as defects.

# SEVERITY SYSTEM

Use exactly these severity categories:

```text
[CRITICAL]
[MAJOR]
[MINOR]
[UI/UX]
[MISSING FEATURE]
```

Additionally, when appropriate, include:

```text
[UNVERIFIED]
```

### CRITICAL

Examples:

* authentication bypass
* cross-tenant data exposure
* privilege escalation
* destructive authorization bypass
* exposed secrets
* severe financial/data integrity issue
* remote code execution
* catastrophic business logic flaw

### MAJOR

Examples:

* significant authorization gap
* important workflow failure
* serious data integrity issue
* significant performance problem
* important missing validation
* major UI workflow failure

### MINOR

Examples:

* maintainability problem
* minor validation issue
* small performance issue
* non-critical technical debt

### UI/UX

Visual, usability, accessibility, responsive design, interaction, or frontend experience problems.

### MISSING FEATURE

Only confirmed functional gaps.

# FINDING FORMAT

Every finding MUST use this structure:

```markdown
### [SEVERITY] Short descriptive title

- **File:** `path/to/file.cs`
- **Line:** `123-137`
- **Symbol:** `MethodName()`
- **Domain:** Security / Backend / Database / UI / Business Logic
- **Confidence:** Confirmed / Probable / Unverified

**Evidence:**

Explain exactly what the code does.

**Problem:**

Explain why this is a problem.

**Impact:**

Explain the real-world consequence.

**Recommendation:**

Provide a concrete remediation strategy.

**Priority:**

P0 / P1 / P2 / P3
```

Do not provide vague recommendations such as:

> "Improve security."

Provide actionable recommendations.
