STEP 3 — SECURITY REMEDIATION
============================================================

------------------------------------------------------------
3.1 API KEY SECURITY
------------------------------------------------------------

Fix every hardcoded API key/default API key identified in the audit.

Requirements:

- Remove hardcoded production API keys.
- Do not leave real secrets in source code.
- Do not place secrets in query strings.
- API keys must be supplied through the appropriate request header.
- Do not accept API keys through URL query parameters.
- Do not log API keys.
- Do not return API keys in API responses.
- Support configuration/environment based secret management.
- Fail safely when required credentials are missing.
- Ensure development/test credentials do not become production credentials.

If an API key is currently:

?apiKey=...

change the implementation so it is NOT accepted from the query string.

Use a proper header such as:

X-Api-Key

or the project's existing secure authentication mechanism.

Also inspect the API key authentication middleware/service.

Do not only change the controller.

Ensure the complete authentication flow is secure.

------------------------------------------------------------
3.2 API KEY → IDENTITY / TENANT BINDING
------------------------------------------------------------

If the API key represents a client/tenant:

Ensure that the authenticated API key resolves to a server-controlled identity.

Do NOT trust:

TenantId
WorkspaceId
CompanyId
UserId

from the request when the value can be derived from the authenticated identity.

Verify that all sensitive operations use the server-resolved tenant/client identity.
