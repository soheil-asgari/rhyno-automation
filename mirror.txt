## 1. Executive Summary

This audit covers the **Rhyno ERP (Rhyno Automation / Hamkaran System-style) ASP.NET Core application** and its satellite projects (worker, tests, workflow UI, Python scripts). The application is a large multi-tenant ERP with modules for Contracts, Finance (vouchers/ledger/trial balance), Warehouse/Inventory, Human Capital, Letters/Office, Workflow/BPMN, Tax Analytics, Invoice Intake, OCR, Mowadiyan tax integration, AI assistant, and Security/ABAC.

The codebase is internally well-engineered in several areas (explicit permission attributes, anti-forgery tokens, tenant isolation infrastructure, audit interceptors, row-level security interceptors, rate limiting, security headers). However, several **CRITICAL** issues were confirmed that materially increase security and integrity risk, centered on:

1. **Default administrative credentials** created unconditionally on every startup.
2. **Trusting the API client-supplied identity** (no tenant/principal distinction for `X-Api-Key`) and a **weak, hardcoded development API key** shipped in configuration.
3. **A path traversal** in the contract attachment download endpoint.
4. **Multiple IDORs** in the Contracts module (payments, deletion, attachment operations trust only the `Contract.Id`/`attachmentId` without object-level access enforcement in the service layer).
5. **Stored XSS** via unsanitized user-supplied contract `HtmlContent`/`Title`/`Terms` rendered through template substitution and served as `text/html`.
6. **Tenant isolation is schema/connection-string based only** — there is **no tenant-ID query filter**, so any query that bypasses the per-tenant connection (or runs under a shared connection) can read cross-tenant data; this is a defense-in-depth and misconfiguration risk.
7. **Hardcoded `guest/guest` RabbitMQ credentials** and placeholder secrets in `appsettings.json`.

## 3. Architecture Overview

### Strengths

- **Clean modularization**: Finance/Inventory/Office/Workflow/Tax separated into `Modules/` with `Application/Domain/Infrastructure` structure.
- **Centralized authorization pipeline**: `PermissionAccessFilter` (global MVC filter) + `PermissionAuthorizeAttribute` + `PermissionAuthorizationHandler` + ABAC service + a `NormalizeInputFilter`.
- **Anti-forgery on by default**: `AutoValidateAntiforgeryTokenAttribute` added globally (Program.cs:318).
- **Audit infrastructure**: `AuditSaveChangesInterceptor`, `AuditLogger`, audit retention pipeline; `RowLevelSecuritySaveChangesInterceptor` for data-scope writes.
- **Tenancy**: `TenantSchemaCommandInterceptor` rewrites schemas; `TenantDbContextModelCacheKeyFactory` handles per-tenant models; background-job coordination exists.
- **Resilience**: rate limiting per tenant + per-AI-user; health checks (db, rabbitmq, redis, disk, memory, external); central slow-request logging.

### Weaknesses / risks

- **God controllers/services** in legacy areas (e.g. `ContractsController` is 448 lines, `ContractService` 1301 lines; `FinancialAppService`/`FinancialInvoiceService` are large).
- **Business logic in controllers**: e.g. `ContractsController` performs file path assembly and model state plumbing.
- **Inconsistent object-level authorization**: some actions call `EnforceAccessAsync`, others do not (see Section 7).
- **Multi-tenancy is connection-string/schema based** with no row-level tenant column filter; risk concentrates in shared-connection or misconfigured deployments.
- **Cross-cutting concerns** (e.g. `IsAdminAsync` implemented per-service with `.Result` blocking) duplicate authorization logic.

### Dependency / coupling concerns

- `ContractService` is coupled to `UserManager`, `OfficeDbContext`, `ITenantSettingsService`, audit logger, template renderer — moderate coupling, but acceptable.
- Many services depend on `IHttpContextAccessor` indirectly, making unit testing harder (mitigated by injectable `IUserContextService`/`IAuditContextProvider` in newer code).

## 4. Critical & Security Vulnerabilities

### [CRITICAL] Default administrative account created on every startup with known credentials

- **File:** `Services/BootstrapAdminSeeder.cs`
- **Line:** `38-98`
- **Symbol:** `SeedAsync()`
- **Domain:** Security / Authentication
- **Confidence:** Confirmed

**Evidence:**
`BootstrapAdminSeeder.SeedAsync` reads credentials from configuration:
```csharp
var email = _configuration.GetValue<string>("BootstrapAdmin:Email") ?? "admin";
var password = _configuration.GetValue<string>("BootstrapAdmin:Password") ?? "admin";
...
var result = await _userManager.CreateAsync(adminUser, password);
```
`appsettings.json` (lines 2-6) sets `"Email": "admin"` and `"Password": "admin"`. `Program.cs:616-627` calls this unconditionally on every startup (with only a try/catch that logs a warning and continues on DB unavailability). Even if strict password policy rejects `"admin"`, the code **bypasses it directly** (lines 85-98): it creates with a random temp password, then overwrites `PasswordHash` with a freshly hashed `"admin"` and calls `SaveChangesAsync` — the comment literally says `// password set directly (bypassed strict policy).`

**Problem:**
A default super-admin with `Role="Admin"`, `CanAccessFinance`, `CanAccessWarehouse`, `CanAccessHumanCapital`, `CanAccessSystemSettings`, `IsManager = true`, and `DataAccessScope = Global` is created with the well-known password `admin`. The seeder runs on every startup and also re-grants all permissions to the Admin role.

**Impact:**
Trivial authentication bypass → full system compromise. Anyone who knows the default credentials (publicly documented in `appsettings.json`) can log in as a global administrator with access to all tenants' data (Global data scope) and all permissions.

**Recommendation:**
1. Remove the default-credentials path entirely. Require an explicit, strong bootstrap password to be provided via environment variable/secret store (`BootstrapAdmin:Password`), and **fail fast** if it is missing or weak.
2. Never fall back to a default (`?? "admin"`), and **remove the direct `PasswordHash` override** path.
3. Only create the admin if `BootstrapAdmin:Enabled = true`, and force a password change on first login.
4. Do not re-grant/scaffold all permissions on every startup; gate permission seeding behind a one-time flag.

### [CRITICAL] Hardcoded, weak, shared development API key shipped in configuration

- **File:** `appsettings.json`
- **Line:** `92-96` (`"Authentication": { "ApiKey": [ "rhyno-dev-api-key-1234567890" ] }`)
- **Symbol:** `Authentication:ApiKey`
- **Domain:** Security / Authentication
- **Confidence:** Confirmed

**Evidence:**
`ApiKeyAuthenticationHandler` validates a single configured key from `ValidApiKeys`. The shipped value is a weak, predictable development key. There is no rotation, no per-client scoping, and (critically, see next finding) the key is accepted via a **query-string parameter** as well as a header.

**Problem:**
If this configuration is deployed to production (and a `docker-compose`/Dockerfile exist in the repo), the API key is a shared static secret that grants the `ApiAccess` role to anyone who extracts it (from logs, URLs, or the source). It cannot identify *which* client is calling, enabling abuse and making revocation impossible without breaking all clients.

**Impact:**
Unauthorized API access; the key-bearing identity is also the only "tenant" context for API calls, so key compromise = data access under that identity.

**Recommendation:**
1. Remove the default key; load API keys from a secret manager (Azure Key Vault / env var) and require explicit configuration at startup.
2. Use strong random keys (≥ 32 bytes) per integration/client, store only hashes (the handler already computes `api_key_hash` — use that for validation instead of the raw key).
3. Reject the query-string form of the key entirely (see next finding).

### [CRITICAL] API key accepted over query string (secret leakage) and key not bound to client identity

- **File:** `Services/Security/ApiKeyAuthenticationHandler.cs`
- **Line:** `14-37` (query param `api_key`, `30-37` extraction)
- **Symbol:** `HandleAuthenticateAsync()`
- **Domain:** Security / Authentication
- **Confidence:** Confirmed

**Evidence:**
```csharp
private const string ApiKeyQueryParam = "api_key";
...
else if (Request.Query.TryGetValue(ApiKeyQueryParam, out var queryValues))
{
    apiKey = queryValues.FirstOrDefault();
}
```
The returned identity is hardcoded: `new Claim(ClaimTypes.NameIdentifier, "api-client")` and `new Claim(ClaimTypes.Name, $"API Client: {apiKey[...]}...")` — every successfully authenticated API key becomes the *same* principal with role `ApiAccess`. There is no per-key client/tenant binding.

**Problem:**
(1) API keys in query strings end up in server logs, reverse-proxy logs, browser history and analytics — this is a secret-leakage vector. (2) All clients authenticated this way share one identity, so authorization cannot distinguish clients, and there is no per-client key revocation or audit attribution.

**Impact:**
Secret exposure + inability to attribute/limit actions to a specific API client.

**Recommendation:**
1. Accept the API key **only** in the `X-Api-Key` header.
2. Load a map of clientId → keyHash → tenant/scope, and build a distinct principal including client identity and tenant.

### [CRITICAL] Path traversal in contract attachment download

- **File:** `Controllers/ContractsController.cs`
- **Line:** `311-321`
- **Symbol:** `DownloadAttachment(int attachmentId)`
- **Domain:** Security
- **Confidence:** Confirmed

**Evidence:**
```csharp
[HttpGet("Contracts/DownloadAttachment/{attachmentId}")]
public async Task<IActionResult> DownloadAttachment(int attachmentId, CancellationToken ct)
{
    var attachment = await _contractService.GetAttachmentAsync(attachmentId, ct);
    if (attachment == null) return NotFound();

    var fullPath = Path.Combine(Directory.GetCurrentDirectory(), "wwwroot", attachment.RelativePath.TrimStart('/'));
    if (!System.IO.File.Exists(fullPath)) return NotFound();

    return PhysicalFile(fullPath, attachment.ContentType ?? "application/octet-stream", attachment.FileName);
}
```
`GetAttachmentAsync` (ContractService.cs:796-800) fetches the record by `Id` only, with **no access check on the parent contract** via `EnforceAccessAsync` (unlike `Edit`/`Delete`).

**Problem:**
1. **Path traversal / arbitrary file read**: `attachment.RelativePath` comes directly from the database row. If an attacker can plant/mutate a `RelativePath` value containing `../` (e.g. via a compromised import, a direct DB write from an integration, or another upload path that persists attacker-controlled relative paths), then `Path.Combine` + `PhysicalFile` would serve **any file under the site root** (and beyond, since `Path.Combine` with an absolute or `..\`-relative path escapes `wwwroot`). There is no re-check that the resolved path stays within `wwwroot/uploads/contracts`.
2. **IDOR**: The action is `[HttpGet]` and only requires the class-level `[PermissionAuthorize("Contract.View")]`; it does not call `EnforceAccessAsync`. Any authenticated user with `Contract.View` permission can download any attachment by enumerating `attachmentId` (1,2,3…), including attachments belonging to contracts they cannot view.

**Impact:**
Arbitrary file disclosure (including `appsettings.json`, configs, other tenants' uploaded documents on shared storage) and cross-user/cross-tenant document disclosure.

**Recommendation:**
1. Resolve the parent contract from the attachment and call `EnforceAccessAsync(contract.ContractId, currentUserId, ...)` before serving.
2. Sanitize/validate `RelativePath` on both write and read: reject any path containing `..`, `:` (drive), rooted paths, or not starting with `uploads/`. Compute the canonical full path and verify it starts with the expected `wwwroot/uploads/contracts` root via `Path.GetFullPath` + prefix check.
3. Store the physical file deterministically server-side (server-generated name under a per-contract directory) and never trust a client/db-supplied path for `PhysicalFile`.

### [CRITICAL] Stored XSS via unsanitized contract HTML template body

- **File:** `Services/Contracts/TemplateRenderingService.cs`
- **Line:** `40-101`; usage in `Services/Contracts/ContractService.cs` (Create `ContractBodyHtml`, `GenerateContractDocumentAsync`, `WrapWithBrandedPrintLayout`)
- **Symbol:** `RenderTemplate()`, `GenerateContractDocumentAsync()`
- **Domain:** Security
- **Confidence:** Confirmed

**Evidence:**
`RenderTemplate` performs pure string substitution with **no HTML encoding**:
```csharp
htmlTemplate = htmlTemplate.Replace(kvp.Key, kvp.Value, StringComparison.OrdinalIgnoreCase);
return htmlTemplate;
```
The substituted values include user-controlled `contract.Title`, `contract.TermsAndConditions`, `contract.Description`, `contract.ClientName`, and the user-authored `ContractBodyHtml`/template `HtmlContent`. `ContractsController.GenerateDocument` returns the rendered result as `text/html`:
```csharp
return Content(html, "text/html", System.Text.Encoding.UTF8);
```
`SaveTemplateAsync` (ContractService.cs:861-891) stores `model.HtmlContent` verbatim.

**Problem:**
A user with `Contract.Edit`/`Contract.Settings` can inject arbitrary `<script>` or event-handler HTML into the template body or contract text fields. When another user generates/opens the contract document (`GenerateDocument`, or the archived `ContractBodyHtml` displayed in views), the script executes in that user's session/CSP context — persisted, cross-user stored XSS. Note the CSP (`script-src 'unsafe-inline' 'unsafe-eval' ...`, SecurityHeadersMiddleware.cs:70) explicitly permits inline scripts, so the injected script would not be blocked by CSP.

**Impact:**
Session/cookie theft, privilege escalation, keylogging, or lateral movement against any user who views a malicious contract or generated document.

**Recommendation:**
1. Sanitize user-supplied HTML before storage/rendering using a strict allow-list HTML sanitizer (there is `Utilities/HtmlSanitizer.cs` — wire it into `SaveTemplateAsync`, `CreateContractAsync`, `UpdateContractAsync`, and rendering).
2. HTML-encode the simple text placeholders (`Title`, `Description`, `Terms`, `ClientName`, etc.) when substituting; allow HTML only for dedicated rich-text fields that have been sanitized.
3. Harden the CSP: remove `'unsafe-inline'`/`'unsafe-eval'` from `script-src` and use nonces/hashes for legitimate inline scripts.

## 5. Backend & Performance

### [MAJOR] IDOR — Contract payments can be added/deleted without object-level access check

- **File:** `Controllers/ContractsController.cs` (`AddPayment`, `DeletePayment` — lines `255-283`) and `Services/Contracts/ContractService.cs` (`AddPaymentAsync` `695-728`, `DeletePaymentAsync` `730-756`)
- **Symbol:** `AddPaymentAsync`, `DeletePaymentAsync`
- **Domain:** Security / Backend
- **Confidence:** Confirmed

**Evidence:**
`AddPayment`/`DeletePayment` require only `[PermissionAuthorize("Contract.Payment")]` and never call `EnforceAccessAsync`. The service methods look up the contract by `model.ContractId` / `contractId` with no ownership/visibility check:
```csharp
var contract = await _context.Contracts.FindAsync(new object[] { model.ContractId }, ct) ?? throw new KeyNotFoundException(...);
```

**Problem:**
Any user possessing the `Contract.Payment` permission can add a payment to or delete a payment from **any contract** (including other users'/contracts they are not assigned to) by supplying an arbitrary `contractId`/`paymentId`. Contrast with `Edit`/`Delete`/`Archive`, which correctly call `EnforceAccessAsync`.

**Impact:**
Financial data manipulation (removing payments from "paid" contracts, adding spurious payments), inconsistent financial status, and unauthorized modification of other users' contracts. Severity is elevated to CRITICAL-adjacent because it is a direct financial write path; it is classified MAJOR here because it still requires the `Contract.Payment` permission.

**Recommendation:**
Call `await _contractService.EnforceAccessAsync(model.ContractId, currentUserId, ct)` at the start of `AddPayment` and `DeletePayment` (and inside the service methods for defense in depth), before any mutation.

### [MAJOR] Synchronous block `IsAdminAsync(...).Result` causes potential deadlock/thread-starvation

- **File:** `Services/Contracts/ContractService.cs`
- **Line:** `42-44` (`IsAdminAsync`) and its callers
- **Symbol:** `IsAdminAsync()`
- **Domain:** Backend / Concurrency
- **Confidence:** Confirmed

**Evidence:**
```csharp
return _userManager.IsInRoleAsync(user, "Admin").Result;
```

**Problem:**
`.Result` synchronously blocks the request thread on an async EF/identity call. Under load this can exhaust the thread pool and, in sync-context environments, deadlock. This is a known anti-pattern (blocks thread + uses the task.Result).

**Impact:**
Latency spikes, thread-pool starvation under concurrent load, intermittent hangs.

**Recommendation:**
Convert to `await _userManager.IsInRoleAsync(user, "Admin")` and make the helper `Task<bool> IsAdminAsync(...)`. Audit the rest of the codebase for `.Result`/`.Wait()`.

### [MAJOR] Financial write path lacks obsolete/lost concurrency token (lost-update risk)

- **File:** `Services/Contracts/ContractService.cs` (`AddPaymentAsync`, `DeletePaymentAsync`, `RecalculatePaymentStatusAsync`), and related financial services
- **Symbol:** `AddPaymentAsync`, `RecalculatePaymentStatusAsync`
- **Domain:** Backend / Business Logic / Database
- **Confidence:** Probable

**Evidence:**
`AddPaymentAsync` recomputes `contract.PaidAmount = contract.Payments.Sum(p => p.Amount) + model.Amount;` on a tracked entity with **no concurrency token / optimistic concurrency** (no `RowVersion` on `Contract`, based on `GetIndexViewModelAsync` projecting plain scalar fields). Two concurrent payment submissions for the same contract can both read `PaidAmount` and overwrite each other.

**Problem:**
Classic lost update: two admins add a payment simultaneously; the second overwrites the first's `PaidAmount`/`RemainingBalance`, and `Sum(p.Amount)` is re-evaluated against a stale in-memory `Payments` collection (which is not freshly loaded), so the stored aggregate can diverge from the actual `ContractPayments` rows.

**Impact:**
Incorrect contract financial status, incorrect "fully paid" determination, financial-report drift.

**Recommendation:**
Use a database-computed aggregate (or re-query payments inside a single transaction with a concurrency token `RowVersion` on `Contract`), and wrap payment add/delete + financial recompute in an explicit transaction with optimistic concurrency (`UPDATE ... WHERE RowVersion = @original`).

### [MAJOR] Exception leakage / missing global JSON error contract for API endpoints

- **File:** `Program.cs` (`UseExceptionHandler`, `UseStatusCodePagesWithReExecute`) and numerous controllers returning bare `BadRequest()`/`NotFound()` without a consistent error body
- **Domain:** Backend / API

### [MAJOR] Rate limiter partition key depends on `ITenantResolver` that can return default for unauthenticated API traffic

- **File:** `Program.cs` (`app.UseRateLimiter` and global limiter, lines `342-378`)
- **Symbol:** `AddRateLimiter` global partition
- **Domain:** Backend / Performance / Security
- **Confidence:** Probable

**Evidence:**
The global limiter partitions by `tenant.TenantId`. `TenantResolver` resolves the tenant (from host/header/query) for every request. If resolution fails or defaults, unauthenticated/ambiguous requests collapse into one partition.

**Problem:**
Attackers hammering many hostnames/keys that resolve to the same tenant share one bucket (good), but a single default partition also means a misbehaving unauthenticated client can exhaust the whole tenant's global budget, causing denial of service for legitimate users of that tenant.

**Impact:**
Potential self-inflicted DoS within a tenant; inconsistent limiting for API-key (non-cookie) callers.

**Recommendation:**
Partition more granularly for anonymous/ambiguous identities (e.g. include IP + a resolution-failure sentinel), and verify `ResolveTenantId` behavior when no tenant is determinable.

## 6. Database & Data Integrity

### [MAJOR] Multi-tenancy relies on per-tenant connection/schema with no tenant-ID query filter (defense-in-depth gap)

- **File:** `Data/ModularDbContext.cs` (`ApplyTenantSchema`, lines `63-69`), `Services/Tenancy/TenantSchemaCommandInterceptor.cs` (`75-91`), `Modules/Persistence/TaxDbContextFactory.cs`
- **Symbol:** `ApplyTenantSchema`, `ReplaceSchema`
- **Domain:** Database / Multi-tenancy / Security
- **Confidence:** Confirmed (design), Probable (exploitability)

**Evidence:**
`ApplyTenantSchema` only calls `modelBuilder.HasDefaultSchema(CurrentDatabaseSchema)`. The `TenantSchemaCommandInterceptor.ReplaceSchema` returns early when `DatabaseSchema` is null/empty/`dbo`:
```csharp
if (tenant == null || string.IsNullOrWhiteSpace(tenant.DatabaseSchema) || string.Equals(tenant.DatabaseSchema, "dbo", ...)) return;
```
In `DatabasePerTenant` mode (the default for the "default" tenant in `appsettings.json`, `"IsolationMode": "DatabasePerTenant"`), schema is `dbo`, so the interceptor does **no tenant filtering**. Isolation is provided purely by resolving a distinct **connection string** per tenant (`TaxDbContextFactory` captures the connection string at construction). There is no EF global query filter or `TenantId` column filter on any entity.

**Problem:**
(1) Any code path that constructs a context with the shared/`DefaultConnection` (e.g. `Program.cs` `GetPlatformConnectionString` falls back to `DefaultConnection`) will see all tenants' data in the same table. (2) If a new tenant is misconfigured to reuse a connection string (the shipped config has exactly one tenant), cross-tenant access is silent. (3) Because `TaxQueryService.AnswerAsync` (TaxQueryService.cs:48-96) queries `db.InvoiceRecords.AsNoTracking()` with no tenant predicate, its safety depends entirely on the per-tenant connection string — a fragile invariant.

**Impact:**
Potential cross-tenant data exposure if connection resolution is ever misconfigured or a shared context is used; architecture is resilient only "by convention."

**Recommendation:**
1. Add a `TenantId` (or equivalent) column + EF global query filter to all tenant entities as defense in depth, even in DatabasePerTenant mode.
2. Centralize a guard that asserts `PlatformDbContext` is the only context allowed on the platform connection.
3. In `TaxQueryService`, add an explicit tenant predicate and validate the resolved tenant before querying.

### [MAJOR] Razor/`Views` contract detail financial visibility depends on server TZ/`CanViewFinancials` but attachment download and payments bypass it

- **File:** `Controllers/ContractsController.cs` (`DownloadAttachment`, `AddPayment`, `DeletePayment`)
- **Domain:** Authentication & Authorization / IDOR

## 8. Frontend UI/UX

### [UI/UX] No explicit loading/error states on several AJAX-heavy dashboards (static analysis only)

- **File:** `wwwroot/js/dashboard.js`, `wwwroot/js/trial-balance.js`, `wwwroot/js/tax-widget.js` (representative)
- **Domain:** UI/UX
- **Confidence:** Probable (static analysis only)

**Evidence:**
Many DataTables/AJAX fetch handlers do not render a persisted empty/error state on failure beyond the default DataTables "no data" text; fetch failures often surface as silent or generic messages.

**Problem/Impact:**
Users can't distinguish "no data" from "request failed" → repeated clicks, stale dashboards, confusion.

**Recommendation:**
Introduce a shared fetch wrapper adding visible loading, empty, and error states (this is the `ProfessionalTable`/`app-ui.js` candidate area to centralize).

### [UI/UX] RTL density is largely consistent, but several fixed-width containers risk horizontal overflow on tablets

- **File:** `wwwroot/css/financial-pages.css`, `wwwroot/css/warehouse-forms.css`, `wwwroot/css/reports.css` (representative)
- **Domain:** UI/UX / Responsive
- **Confidence:** Probable (static analysis only)

**Evidence:**
Multiple rules use pixel-fixed widths (e.g. table/panel min-widths) rather than fluid `100%` + overflow handling; no `max-width:100%; overflow-x:auto` wrappers observed in several grid/table areas.

**Impact:** Horizontal scroll/reflow on smaller viewports.

**Recommendation:** Wrap data grids in `overflow-x:auto` and replace hard pixel widths with `min-width` on inner tables; add responsive breakpoints for the 4-zone shell (header/menu/taskbar/desktop).

### [UI/UX] Inconsistent loading state on form submit (double-submit protection)

**Evidence:** Several POST forms bind submit without immediately disabling the button; server round-trips can be re-fired on double click. No shared `isSubmitting` guard found across all critical forms.

**Impact:** Duplicate submissions (duplicate payments/documents).

**Recommendation:** Add a global submit-guard (disable + `data-submitting`) on all save forms.

### [UI/UX] `console.log` statements present in production JS

## 9. Business Logic

### [MAJOR] Contract `Create` allows setting `AssignedUserId`/`CustomerId`/arbitrary `Status` from client without authorization of assignment

- **File:** `Controllers/ContractsController.cs` (`Create`, `Edit`) + `Services/Contracts/ContractService.cs` (`CreateContractAsync`)
- **Domain:** Business Logic / Authorization
- **Confidence:** Confirmed

**Evidence:** The binding model includes `AssignedUserId`, `CustomerId`, `Status`, `ContractType`, `TotalAmount`. `CreateContractAsync` persists all of them directly with no check that the acting user may assign users or set a paid `TotalAmount`/status.

**Problem:** A low-privilege creator can assign a contract to another user (or set it to `Approved`/`Active` status and an arbitrary amount) without approval, bypassing workflow intent.

**Impact:** Business-rule bypass (unauthorized assignment/approval), financial misstatement.

**Recommendation:** Restrict `AssignedUserId`/`Status` transitions to authorized roles/approval workflow on create/edit; validate that target user is within the same tenant.

### [MAJOR] Deleting a contract does not delete its stored attachment files from disk

- **File:** `Services/Contracts/ContractService.cs` (`DeleteContractAsync` `576-584`)
- **Domain:** Business Logic / Reliability
- **Confidence:** Confirmed

**Evidence:** `DeleteContractAsync` removes the `Contract` (cascade removes attachments rows), but never deletes the files under `wwwroot/uploads/contracts/{id}`.

**Problem:** Orphaned files accumulate; more importantly, files remain physically readable if paths linger; storage bloat.

**Impact:** Storage leak + residual sensitive data on disk (compliance).

**Recommendation:** Delete the per-contract upload directory on contract delete; consider tombstone/archive directories for legal-hold (there is `AddLegalHoldToDocumentArchive` migration — reuse same policy).

### [MAJOR] `RecalculatePaymentStatusAsync` and payment recompute use in-memory `Payments` collection (stale data)

- **File:** `Services/Contracts/ContractService.cs` (`109-129`, `695-756`)
- **Domain:** Business Logic
- **Confidence:** Probable

Covered in Section 5 (concurrency/lost-update). Duplicate classification noted here for the workflow impact: payment status can be wrong after concurrent edits.

### [MINOR] Inconsistent financial visibility rule (`CanUserViewFinancials`) vs. payment mutation

Covered in Section 7. Business impact: view hides financials but mutation endpoints don't.

### [MINOR] `UnarchiveContractAsync` always sets `Status = Active`

- **File:** `Services/Contracts/ContractService.cs` (`679-689`)
- **Domain:** Business Logic / Edge case
- **Confidence:** Confirmed

**Evidence:** On unarchive the status is forcibly set to `Active`, discarding the prior status (e.g. `Completed`, `Expired`, `ExpiringSoon`).

**Impact:** A completed/expired contract restored becomes "Active" incorrectly.

**Recommendation:** Restore the pre-archive `Status` (store it in a field) or require explicit re-selection.
