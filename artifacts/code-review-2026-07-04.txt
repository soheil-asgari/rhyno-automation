1) XSS سمت کلاینت در چند View به‌خاطر تزریق مستقیم داده‌های داینامیک در innerHTML/template string
   فایل‌ها:
   - Views/WorkInbox/Index.cshtml:459, 474-480
   - Views/ProcessAnalysis/Index.cshtml:340-367
   مشکل:
   - در WorkInbox مقادیر `groupName`, `item.title`, `item.icon`, `item.priorityCssClass` و بقیه‌ی فیلدهای آبجکت بدون escape داخل `innerHTML` و template literal رندر می‌شوند.
   - در ProcessAnalysis هم داده‌های API مثل `processName`, `stepName` و بقیه بدون escape مستقیم وارد DOM می‌شوند.
   چرا بد است:
   - اگر هر کدام از این فیلدها از دیتابیس/ورودی کاربر/سرویس دیگر آلوده شوند، اجرای اسکریپت دلخواه داخل مرورگر کاربر ممکن می‌شود.
   - این دیگر «کد تمیز نیست» نیست؛ این یک باگ امنیتی واقعی است.
   شدت:
   - بحرانی. مخصوصاً WorkInbox چون داده‌های workflow معمولاً از مسیرهای متعدد می‌آیند و سطح حمله بزرگ است.

2) آپلود فایل workflow بدون هیچ whitelist واقعی و مستقیماً زیر WebRoot
   فایل:
   - Services/WorkflowService.cs:515-536
   مشکل:
   - فایل کاربر با نام sanitize حداقلی ذخیره می‌شود، اما extension/type/size/policy معتبر بررسی نمی‌شود.
   - مسیر پیش‌فرض هم داخل `_environment.WebRootPath/uploads/...` است؛ یعنی فایل آپلودی بالقوه از وب‌سرور قابل دسترسی مستقیم است.
   چرا بد است:
   - این طراحی برای آپلود سازمانی فاجعه است: فایل مخرب، فایل HTML/JS، payload فیشینگ، یا فایل حجیم بدون کنترل می‌تواند مستقیم منتشر شود.
   - `ContentType` کلاینت‌فرست است و قابل اعتماد نیست.
   شدت:
   - بحرانی. آپلود باید خارج از web root، با allow-list سختگیرانه، اسکن و authorization دانلود جداگانه انجام شود.

3) bootstrap برنامه با copy-paste پوسیده: ثبت سرویس‌ها تکراری و متناقض
   فایل:
   - Program.cs:47-55
   - Program.cs:149-176
   مشکل:
   - چند سرویس tenant دوبار ثبت شده‌اند.
   - مجموعه‌ای از سرویس‌های workflow/outbox/notification هم دوبار پشت‌سرهم ثبت شده‌اند.
   چرا بد است:
   - این فقط شلوغی نیست. در DI مایکروسافت، resolve تکی آخرین registration را می‌گیرد ولی `IEnumerable<T>` همه را. این یعنی رفتار runtime بسته به نحوه resolve می‌تواند غیرشفاف و متناقض شود.
   - این سطح از duplication در نقطه‌ی bootstrap یعنی هیچ کس دیگر با اطمینان نمی‌داند startup واقعاً چه dependency graphی می‌سازد.
   شدت:
   - بالا. قبل از هر توسعه‌ی بیشتر باید cleanup شود.

4) migration tenantها موقع startup کل وب‌اپ را hostage می‌گیرد
   فایل:

   - Services/Tenancy/TenantMigrationOrchestrator.cs:74-98

   چرا بد است:

   - این design برای production خطرناک است؛ وب‌اپ نباید برای migration همه tenantها روی startup بلوکه شود.
   شدت:
   - بالا. migration باید job عملیاتی/کنترلی جدا باشد، نه پیش‌نیاز بالا آمدن app.

5) race condition در تولید SequenceNumber رویدادهای workflow
   فایل:
   - Services/WorkflowService.cs:1421-1445
   مشکل:
   - با `MaxAsync(...SequenceNumber) + 1` شماره رویداد بعدی محاسبه می‌شود.

جمع‌بندی رک
========================================

- بزرگ‌ترین ضعف فعلی شما «نبود مرز معماری» است: bootstrap شلخته، controller چاق، service غول‌پیکر، و frontendهایی که هم encoding مشکل دارند هم XSS.
- اگر همین امروز فقط سه چیز را درست کنید، به‌ترتیب این‌ها هستند:
  1. حذف XSSهای `innerHTML` و امن‌سازی upload
  2. cleanup کامل `Program.cs`
  3. شکستن `WorkflowService` و `FinancialController` به application services / query handlers / UI models واقعی

این گزارش روی یافته‌های واقعی و قابل استناد نوشته شده، نه روی سلیقه‌ی کدنویسی.
