بررسی عمیق‌تر بک‌اند و فرانت‌اند رو هم انجام دادم. یه چیز جدید و خیلی خطرناک‌تر از هر چیزی که قبلاً گفتم پیدا کردم. کل لیست جامع رو اینجا می‌ذارم.
۱. بمب واقعی: SSRF + AI-to-SQL در ManagementDashboardController
این مهم‌ترین یافته‌ی کل بررسیه، حتی از XSS خودتون هم بدتره.
Controllers/ManagementDashboardController.cs یه فیچر داره که:

یه DatabaseConnectionRequest از کلاینت می‌گیره با فیلدهای Host، Port، DatabaseName، Username، Password (Models/ManagementDashboardViewModels.cs)
با همین مقادیر که کاربر می‌فرسته، مستقیم new SqlConnection(...) می‌سازه و به هر آدرسی که کاربر بده وصل می‌شه (TrustServerCertificate = true هم به‌صورت پیش‌فرضه، یعنی اعتبارسنجی TLS هم عملاً خاموشه)
بعد schema اون دیتابیس رو می‌خونه، به AI می‌ده تا SQL بسازه
SQL تولیدشده توسط AI رو فقط با یه regex ساده (AiSqlSafetyService) چک می‌کنه که «SELECT هست یا نه» و بعد مستقیم روی همون کانکشن اجرا می‌کنه

این یعنی:

SSRF واقعی: سرور شما به هر IP/پورت داخلی یا خارجی که کاربر مشخص کنه وصل می‌شه. یه کاربر لاگین‌شده می‌تونه سرور شما رو مجبور کنه به شبکه‌ی داخلی سازمان (دیتابیس‌های دیگه، سرویس‌های internal) وصل بشه و پورت‌اسکن کنه.
دفاع regex-based در برابر AI-generated SQL عملاً امنیت واقعی نیست. بلوک‌کردن کلمه‌کلیدی هیچ‌وقت کامل نیست؛ چیزی مثل UNION SELECT از information_schema، یا CTEهای سنگین برای DoS، از این regex به‌راحتی رد می‌شن چون فقط دنبال INSERT/UPDATE/DELETE/DROP/... و کاراکترهای خاص می‌گرده، نه معنای واقعی کوئری.
کل این مسیر فقط پشت [Authorize] ساده‌ست، نه یه پالیسی سخت‌گیرانه‌ی مخصوص ادمین ارشد. یعنی هر کاربر معمولی که به این کنترلر دسترسی داشته باشه می‌تونه از سرور شما به‌عنوان یه SQL/SSRF proxy استفاده کنه.

برای یه محصول ERP که قراره به‌عنوان enterprise-grade فروخته بشه، این نوع طراحی همون چیزیه که تیم امنیتی خریدار همون روز اول deal رو متوقف می‌کنه.

۲. بک‌اند — معماری

دو معماری هم‌زمان زنده‌ست. یه پوشه‌ی Modules/ با ساختار نسبتاً تمیز DDD (Domain/Infrastructure/Application برای Finance، Workflow، Platform، Identity، Inventory) کنار یه لایه‌ی قدیمی Controllers/ + Services/ که مستقیم روی همون entityها کار می‌کنه (مثلاً هم Controllers/FinancialController.cs و هم Modules/Finance/Application/FinanceLedgerService.cs هر دو منطق financeی رو لمس می‌کنن). این یعنی رفاکتور نصفه‌کاره؛ بدتر از داشتن یه معماری بد، چون الان هیچ دولوپری مطمئن نیست منطق جدید کجا باید بره.
God Controllers/Services:

Controllers/WarehouseController.cs → ۲۸۵۳ خط
Controllers/FinancialController.cs → ۱۸۹۷ خط، ۱۴ dependency تو constructor
Services/WorkflowService.cs → ۱۸۷۶ خط، همه‌چیز از routing تا امضای دیجیتال تا SLA رو قورت داده، و داخلش new DecisionEngine()/new WorkflowDefinitionSelector() می‌سازه که یعنی DI رو دور زده.


DI Registration تکراری در Program.cs — چند سرویس (tenant، workflow، outbox، notification) دوبار ثبت شدن. رفتار IEnumerable<T> در برابر resolve تکی از هم متفاوت می‌شه، یعنی رفتار runtime غیرقابل‌پیش‌بینیه.
Migration همه‌ی Tenant ها موقع Startup انجام می‌شه (Services/Tenancy/TenantMigrationOrchestrator.cs) — یعنی availability کل اپ گره خورده به سالم‌بودن همه‌ی دیتابیس‌های همه‌ی مشتری‌ها. یه tenant کند یا خراب، کل اپ رو بالا نمیاره.
Race condition در تولید SequenceNumber رویدادهای workflow با MaxAsync(...) + 1 — دو ریکوئست هم‌زمان به‌راحتی collision می‌سازن.
آپلود فایل ناامن (Services/WorkflowService.cs): بدون allow-list واقعی، مستقیم زیر WebRootPath، یعنی فایل آپلودی از وب مستقیم قابل‌دسترسیه. ContentType هم از کلاینت گرفته می‌شه که قابل‌جعله.


۳. بک‌اند — تست و کیفیت

فقط ۴ فایل تست برای سیستمی با ۳۱ کنترلر، ۷۸ سرویس و ۱۰۸ ویو. عملاً پوشش تست معنادار نداره، مخصوصاً روی مسیرهای مالی که اشتباه توش گرون تمومه.
توی task.txt یه exception هندل‌نشده‌ی واقعی از production/dev کامیت شده (Finance account 'AR' is not configured) — یعنی این باگ حداقل یه بار رخ داده و به‌جای فیکس یا issue، به‌عنوان فایل تو روت ریپو رها شده.
تو package.json یه دیپندنسی کاملاً بی‌ربط هست: @codesandbox/sandpack-react. این پروژه ASP.NET MVC + Tailwind هست، نه یه React sandbox app. یعنی یا کپی‌پیست از یه template دیگه‌ست یا AI-generated boilerplate هست که هیچ‌وقت پاک نشده — نشونه‌ی dependency hygiene ضعیف.


۴. فرانت‌اند — فریمورک/استایل

دو فریمورک CSS هم‌زمان vendored و استفاده می‌شن: Bootstrap و Tailwind. مثلاً Views/Financial/EditInvoice.cshtml و Views/Financial/SeasonalTaxReport.cshtml هر دو کلاس‌های btn btn-* بوت‌استرپ و کلاس‌های utility تیلویند رو با هم دارن. این یعنی جنگ specificity، باندل حجیم‌تر، و زبان طراحی ناهماهنگ.
۴۲ فایل CSS جداگانه در wwwroot/css، از جمله سه نسخه‌ی موازی از «ریفرش بصری»: visual-refresh.css، visual-refresh-core.css، visual-refresh-legacy.css و دو main.css / main-legacy.css / main-foundation.css. این الگوی کلاسیک redesignهای پشت‌سرهم بدون پاک‌کردن نسخه‌ی قبلیه — بدهی فنی فرانت به‌شدت بالاست.
Stack فرانت هنوز عمیقاً روی jQuery + jQuery Validation + DataTables (نسخه‌های vendored قدیمی) بسته‌ست، هم‌زمان با Tailwind مدرن. یعنی دو نسل تکنولوژی فرانت با هم قاطی شدن بدون یه استراتژی migration مشخص.
هیچ bundler/module system واقعی نیست (Webpack/Vite/esbuild)؛ فقط اسکریپت‌های جدا جدا با <script src>. برای پروژه‌ای به این حجم، یعنی صدها HTTP request جدا برای asset ها یا نیاز به concat دستی، و صفر tree-shaking/minification خودکار برای JS.


۵. فرانت‌اند — کیفیت کد

۳۰ ویو دارن <script> اینلاین و ۳۹ مورد style= اینلاین، هم‌زمان با اینکه فایل‌های JS جداگانه هم برای بعضی صفحات (letter.js, settings.js, ...) وجود دارن. یعنی الگوی ناهماهنگ — گاهی جدا، گاهی اینلاین، بدون قاعده‌ی مشخص.
متن‌های فارسی و حتی identifierهای جاوااسکریپت mojibake/خراب شدن در چند View مهم (WorkInbox/Index.cshtml, AuditDashboard/Index.cshtml, ProcessAnalysis/Index.cshtml). برای یه محصول فارسی‌زبان که قراره فروخته بشه، این embarrassing و مستقیماً روی اعتماد مشتری اثر می‌ذاره.
XSS واقعی: در WorkInbox/Index.cshtml و ProcessAnalysis/Index.cshtml، دیتای داینامیک (groupName, item.title, processName, ...) بدون escape مستقیم داخل innerHTML/template literal رندر می‌شه.
الگوی ذخیره‌سازی ناهماهنگ بین ماژول‌ها: WorkInbox برای saved views فقط localStorage (client-only) استفاده می‌کنه، در حالی که Leaves و Letters سمت سرور sync دارن. یعنی رفتار محصول بین ماژول‌ها یکدست نیست، و saved view بین دستگاه‌ها منتقل نمی‌شه.
